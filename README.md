# DPW (DPWeb)

DPWeb is a German-language activity-planning application for scouts. It manages
activities and timed programs, responsibilities and materials, attachments,
public activity shares, registration forms, reusable templates, mail and
WordPress/EventON publishing. Users have departments, roles and configurable
permissions; the Vue/TypeScript PWA supports live updates and browser push.

## Intentional Easter egg

The bug-report dialog commemorates the first external issue (#88): activating
its title five times reveals the original quote. Dismissing it or closing the
dialog resets the interaction; preserve this behavior when changing the dialog.

The C++ backend serves the API and WebSockets. Nginx serves the frontend and
proxies `/api/` to the backend (removing the prefix) and `/ws` for live updates.
PostgreSQL holds persistent application data; Redis is a disposable cache.

**Start here:** [production setup](#production-setup),
[development](#development-and-test-data), [tests](#tests),
[operator reference](docs/operations.md), [AI/contributor instructions](AGENTS.md).
The operator reference is in German, matching the application's UI.

## Requirements

Use Docker Engine/Desktop with Linux containers and a current Docker Compose
plugin. Shell examples below use **Bash**; Make targets require GNU Make.
On Windows, use WSL2 with Docker integration for those shell/Make commands.
Node.js is only needed on the host for the direct frontend/documentation commands;
the supported frontend build image is listed below.
Upgrade tests require Compose 2.24.4+; documentation checks require the
`docker compose config --no-env-resolution` option. CI supplies these tools.

Run commands from the repository root unless a snippet explicitly changes directory.

## Production setup

[docker-compose.yml](docker-compose.yml) uses published GHCR images; it does not
build this checkout.

```bash
cp .env.example .env
# Edit .env before starting: replace DPW_CONFIG_ENCRYPTION_KEY with a strong random secret.
# For example, generate a value with: openssl rand -hex 32
docker compose -f docker-compose.yml pull
docker compose -f docker-compose.yml up -d --wait
docker compose -f docker-compose.yml ps
```

Open the browser URL in the repository reference above. Complete the initial
`/setup` screen with Microsoft Entra ID/Azure tenant ID, client ID, client secret
and a real contact email. Register the frontend's exact origin as the SPA redirect
URI in Entra ID; the frontend uses `window.location.origin`. Login requests use
`openid`, `profile`, `email`; interactive Graph mail/people features request
`Mail.Send`, `People.Read` as implemented in
[useAuth.ts](frontend/src/composables/useAuth.ts).

## Selbst gehostete Rechtschreibprüfung

Geänderte Programmpunkt-Beschreibungen werden nach einer kurzen Schreibpause
lokal geprüft. Erkannte Stellen werden in unterstützten Browsern markiert; ein
Klick darauf zeigt Vorschläge, die nur auf Klick übernommen werden.
Als falsch markierte Wörter lassen sich per Klick ins persönliche Wörterbuch
aufnehmen. Im Profil lässt sich die standardmässig aktive integrierte Prüfung
abschalten; dann übernimmt die Rechtschreibprüfung des Browsers. Details zu Dienst, Ressourcen und Datenschutz
stehen in der [Betriebsreferenz](docs/operations.md#selbst-gehostete-rechtschreibprüfung).

## Geteilte Aktivitäten und öffentliche Formulare

Freigabelinks unter `/shared/:token` zeigen Aktivitäten mit gut lesbaren Texten
und einer gegliederten Kartenansicht. Geteilte Aktivitäten und öffentliche
Formulare unter `/forms/:slug` zeigen das DPWeb-Logo als Link zur Startseite.
Die Links verwenden die konfigurierte öffentliche Basis-URL (`DPW_PUBLIC_URL`
bzw. **System > Einstellungen**); ohne Konfiguration bleibt die Startseite
auf derselben Instanz.

**In DPWeb öffnen** führt von der geteilten Aktivität zu `/activities/:id`.
Ohne Anmeldung erscheint dort die normale Anmeldung; nach erfolgreichem Login
wird dieselbe Aktivität geöffnet. Der Freigabelink gewährt keine zusätzlichen
Zugriffsrechte in der angemeldeten Ansicht. Programmbeschreibungen und ihre
eingebetteten Bilder bleiben in der Freigabeansicht erhalten; nur Bilder, die
zur freigegebenen Aktivität gehören, werden über den bestehenden Freigabelink
geladen. Freigabelinks und öffentliche Formularantworten bleiben ohne Anmeldung
nutzbar.

## Bilder in Programmpunkten

In der Beschreibung eines Programmpunkts lassen sich Bilder **zwischen Text**
einfügen: im fokussierten Beschreibungseditor auf **Bild** klicken und Dateien
auswählen, oder ein kopiertes Bild direkt einfügen. PNG, JPEG, GIF und WebP bis
**10 MiB pro Bild** werden unterstützt; SVG und leere Dateien werden abgelehnt.
Gemischte Zwischenablage-Inhalte behalten bereinigten Text und die Bildpositionen.
Zwischenablage-HTML wird vor der Bildverarbeitung mit DOMPurify bereinigt;
gespeicherte Beschreibungen verwenden weiterhin die vorhandene HTML-Bereinigung.
Externe Bild-URLs werden beim Einfügen nicht übernommen: stattdessen die Bilddatei
hochladen oder das Bild selbst kopieren. Uploadfehler bleiben sichtbar; vor dem
Wechsel zur Ansicht wird ein laufender Upload abgeschlossen.

Die Bildbytes liegen dauerhaft als `BYTEA` in PostgreSQL (`program_images`),
getrennt von der Anhangsliste. Beschreibungen speichern nur stabile
`/api/program-images/<id>`-Referenzen, niemals Blob-URLs oder Anmeldetokens.
Schreibzugriffe verwenden dieselbe Aktivitätsberechtigung wie Anhang-Uploads;
Bildabrufe prüfen die Leseberechtigung ihres Elternobjekts. Ein Freigabelink zeigt
nur Bilder, die tatsächlich in den Programmpunkten dieser freigegebenen Aktivität
stehen. Editieransicht, normale Ansicht, Ideenkiste und Freigabeansicht laden
Bilder berechtigt nach; der Word-Export bettet sie in der Textreihenfolge ein.
Beim Kopieren einer Aktivität oder Speichern/Übernehmen über die Ideenkiste werden
berechtigt gelesene Bilder innerhalb der Schreibtransaktion für das neue
Elternobjekt kopiert. Das endgültige Löschen eines Elternobjekts entfernt dessen
Bilder; Kopien bleiben erhalten. Entfernte Bildreferenzen geben keine öffentliche
Zugriffsmöglichkeit frei. Nicht mehr referenzierte Bytes bleiben bis zum
endgültigen Löschen des Elternobjekts erhalten; beim Abbrechen einer Bearbeitung
werden neu hochgeladene Bilder nach erfolgreichem Zurücksetzen entfernt.

## Programmpunkte aus der Ideenkiste

Im Bearbeitungsmodus einer Aktivitaet ueber **Aus Ideenkiste** einen gespeicherten
Programmpunkt auswaehlen. Titel, Dauer und formatierte Beschreibung stehen direkt
im neuen Programmblock zur Bearbeitung bereit; ein Neuladen ist nicht erforderlich.
Weitere Aenderungen werden wie bei manuell angelegten Programmpunkten automatisch
gespeichert.

## Aktivitäten bearbeiten

Programmpunkte sind im Bearbeitungsmodus zunächst eingeklappt und lassen sich
unabhängig voneinander öffnen oder mit **Alle öffnen / Alle schliessen**
gemeinsam ein- und ausklappen. Änderungen bleiben beim Einklappen erhalten; die
Reihenfolge kann weiterhin über den Ziehgriff angepasst werden.

Die Schaltfläche **Auswertung** oben auf der Aktivität öffnet am Aktivitätstag
(am selben Datum unabhängig von der Uhrzeit) eine rollenabhängige Auswertung:
Verantwortliche erfassen tatsächliche Teilnehmendenzahl sowie Start- und Endzeit,
alle anderen Personen bewerten die Aktivität von 0 bis 10 und ergänzen einzelne
Punkte zu Erfolgen, Verbesserungen und Massnahmen sowie allgemeines Feedback.
Die gesammelten Rückmeldungen erscheinen als Tabelle mit farbiger Bewertung.
In der Aktivitätenübersicht zeigt der Feedback-Durchschnitt nur abgegebene
0–10-Bewertungen; ohne bewertete Rückmeldungen wird kein Durchschnitt angezeigt.
Details zu Zugriff und Speicherung stehen in der
[Betriebsreferenz](docs/operations.md).

**Do not expose an unfinished setup publicly:** missing setup fields can be set
without login while setup is incomplete. The first login is **not** a generic
first-user-admin bootstrap. Current role assignment gives ordinary new users
`Mitglied` in `Allgemein`, with an admin override when the verified email contains
`admin`; review [the login handler](backend/src/handlers/users.cpp) and your tenant
accounts before provisioning administrator access.

The Compose file contains default database credentials and mounts the host
Docker socket into the backend for administrative container operations. Treat
this as a trusted-host deployment, not a hardened public-host template: restrict
host access, review credentials in **both** database and backend configuration,
and put public traffic behind your HTTPS reverse proxy.

## Configuration

[.env.example](.env.example) lists required configuration and optional overrides.
`DPW_CONFIG_ENCRYPTION_KEY` is required for startup and encrypts sensitive settings
stored in PostgreSQL. **Keep the same key across restarts/upgrades and back it up
securely with your database**; changing it is not a supported key-rotation procedure.
Never commit a real `.env`, tokens, passwords or encryption keys.

For application settings defined in
[app_config.cpp](backend/src/infra/app_config.cpp), a nonempty ENV override wins
over the database/default and locks the corresponding UI field. Overrides are
also imported into the database at startup: removing an ENV alone does not reset
the saved value. Admins manage unoverridden settings under **System > Einstellungen**.
Production loads `.env`, then optional `stack.env` (later values override earlier
ones); development requires `.env`. Compose's explicit `environment` entries
take precedence over these files; in development that includes an
`AZURE_CLIENT_SECRET` fallback, so provide a real ENV value for real Microsoft login.

Set `DPW_PUBLIC_URL` to the externally reachable origin, or configure it in the
admin UI. It is used for public links and scheduled reminders; missing it makes
the reminder job fail explicitly. Web-push VAPID keys are generated and stored
encrypted automatically unless supplied. HTTPS/browser permission and a push
subscription are still required for browser delivery. Optional integration
settings cover MiData, WordPress/EventON and GitHub issue creation.

Do not use `DEBUG=true`: no such runtime switch enables debug login.
Authentication bypass and the frontend user selector are build-time options;
production images disable both. `VITE_BACKEND_URL` is a Vite-development setting,
not a production Nginx routing override.

## Development and test data

[docker-compose-dev.yml](docker-compose-dev.yml) builds local sources.
Its defaults are Release builds with debug authentication disabled.
`make rebuild` and `make fresh` explicitly enable **Debug + debug authentication**.
Do not deploy those images as production.

```bash
cp .env.example .env
# Replace the encryption-key placeholder as in production.
make fresh
```

**`make fresh` deletes the development database volume**, rebuilds, waits for the
services, then loads [db/seed.sql](db/seed.sql). For disposable debug login without
real Microsoft credentials, set the following **test-only** values in `.env`
before running it (the development backend supplies a debug client-secret fallback):

```dotenv
AZURE_TENANT_ID=debug-tenant
AZURE_CLIENT_ID=debug-client
DPW_VAPID_SUBJECT=mailto:dev@example.invalid
DPW_PUBLIC_URL=http://localhost:8000
```

Those values satisfy the setup gate; use the debug selector to sign in as a seeded
user, not Microsoft login. For real Microsoft login, complete setup with real
credentials and contact email instead. Seed data is never for production.

| Command | Purpose / important caveat |
| --- | --- |
| `make up` / `make down` | Start / stop development containers without rebuilding or deleting volumes |
| `make rebuild` | Rebuild and recreate development containers with debug auth |
| `make rebuild-backend` / `make rebuild-frontend` | Rebuild only the selected development service |
| `make build-prod` / `make rebuild-prod` | Local Release builds without debug auth, still using the **development** Compose file |
| `make logs` / `make logs-backend` | Follow container logs |
| `make ps` / `make db-shell` | Inspect development services / open PostgreSQL shell |
| `make db-seed` | **Delete the development DB volume**, restart, then load test data |
| `make generate-vapid-keys` | Optional manual VAPID generation (requires host Node.js) |
| `make clean` | **Remove development volumes and local service images** |

`make up` does not force a rebuild or enable debug auth on its own. Use `make down`
(without `-v`) when you want to preserve development data. Do not run reset/cleanup
commands against valuable data or a shared environment.

For faster frontend iteration, keep a backend running, use the loopback address
from the `port backend 8080` command above as `VITE_BACKEND_URL`, then:

```bash
cd frontend
npm ci
VITE_BACKEND_URL=http://127.0.0.1:<backend-port> VITE_ENABLE_DEBUG_AUTH=1 npm run dev
```

Replace `<backend-port>` before running; use `VITE_ENABLE_DEBUG_AUTH=1` only with a
debug-enabled backend. Vite proxies `/api` and `/ws`; it does not start the backend.

## Vorlagenvariablen und Mail-Vorlagen

Die vorhandenen Variablen (z. B. `{{titel}}`, `{{datum_kurz}}`, `{{ort}}`
und `{{abteilung}}`) funktionieren auch im Mail-Betreff, im Formular-Titel
und im Event-Titel.

- Unter **Admin > Vorlagen > Mail** koennen pro Abteilung mehrere benannte
  Vorlagen mit Empfaengern und CC verwaltet werden. Eine Vorlage kann als
  Standard gesetzt werden; sie wird beim Oeffnen des Mailversands automatisch
  geladen. Die Vorlagen erscheinen als Liste mit Standardstatus und Vorschau;
  neue Vorlagen oeffnen direkt den Editor und werden erst mit **Speichern**
  angelegt. Aenderungen an bestehenden Vorlagen werden gespeichert, bevor
  **Zurueck** zur Liste fuehrt. Im Mailversand kann zwischen Vorlagen gewechselt
  werden.
  Wenn dabei eigene Aenderungen ueberschrieben wuerden, wird vorher nachgefragt.
  Bestehende Mailvorlagen bleiben beim Datenbank-Upgrade als Standard erhalten.
- Unter **Admin > Vorlagen > Events** kann pro Stufe eine Event-Vorlage
  bearbeitet werden. Die Stufenauswahl bleibt auch im Editor verfuegbar;
  ausstehende Aenderungen werden vor einem Stufenwechsel gespeichert.
- Mail-Betreff und Event-Titel werden beim Laden der Vorlage als Klartext
  aufgeloest; `{{formular_link}}` und `{{formular_link|Anmelden}}` ergeben
  dort die Formular-URL statt HTML. Die Vorschau kann vor dem Versand bzw.
  Publizieren bearbeitet werden.
- Der Name einer Formularvorlage wird beim Erstellen als Formular-Titel
  uebernommen. Ein selbst eingegebener Titel bleibt beim Vorlagenwechsel
  erhalten. In Vorlagen und Entwuerfen bleiben die Variablen stehen.
  Beim Erstellen wird der Titel mit den aktuellen Aktivitaetsdaten
  aufgeloest und gespeichert, sodass auch Verwaltung und Editor sofort
  den fertigen Titel anzeigen. Variablen in den Fragen werden weiterhin
  erst im oeffentlichen Formular ersetzt.
- Unbekannte Variablen bleiben unveraendert. Rich-Text-Inhalte behalten
  ihre bisherige Formatierung und Linkdarstellung.

## Operations, upgrades and CI

**System > Audit Log** provides an admin-only durable journal with configurable
retention. **System > Cron-Jobs** exposes cleanup/reminder job health and
pause/resume controls. Reminder preferences live in the profile and use each
user's department/read permissions; reminder scheduling is server-side.
**System > Wartungsfenster** supports manual and scheduled/recurring maintenance:
admins stay in the app with a persistent active-maintenance banner while other
sessions are redirected. Maintenance is an access/UX control, not a substitute
for stopping writers and taking backups.

The backend bundles [db/init.sql](db/init.sql) and synchronizes the schema on
startup, including existing databases. There are no separate migration files.
Keep schema changes idempotent and intentional transformations explicit.
Take and verify an external backup before upgrades; the startup snapshot/restore
mechanism is temporary recovery, **not a backup or a guaranteed downgrade path**.
Keep PostgreSQL data and the configuration encryption key together.

To update a deployment, select a matching backend/frontend image pair, then use
`docker compose -f docker-compose.yml pull` followed by
`docker compose -f docker-compose.yml up -d --wait`; inspect health and logs.
`latest` is mutable; pin both images to a matching release/revision for a
controlled rollout. Changing the PostgreSQL major version needs its own migration
procedure, not just an image-tag edit.

[CI](.github/workflows/ci.yml) runs documentation, frontend/backend unit tests,
fresh-install smoke/schema/API, audit, reminders and maintenance regressions on
PRs to `main`, pushes to `main` and `v*` tags. Only pushes publish production GHCR
images (Release, debug auth off). Tags include `main`/`latest` for main pushes,
`sha-<short-commit>` and the `v*` release tag for tagged pushes.
[Upgrade Compatibility](.github/workflows/upgrade.yml) separately upgrades the
last successfully published matching main image pair with persisted data to the
PR production images, compares against a fresh candidate schema, checks restart
idempotence and exercises negative controls. It does not cover every old release
or PostgreSQL major upgrade.

[PR Debug Deploy](.github/workflows/pr-debug-deploy.yml) is a separate,
approval-gated `pr-debug` environment on a self-hosted runner. It rebuilds and
seeds a disposable debug stack, publishes its Cloudflare URL in a PR comment, and
cleans up only that PR's tunnel, Compose stack and volumes on close or merge.
Cleanup is idempotent and reports failures; it does not sweep deployments for
other PRs. Synchronizing a PR redeploys and resets its debug data after approval;
approve the final head only after the other applicable checks succeed. It is not
the production publication or persisted-upgrade test.

See [the detailed operator reference](docs/operations.md) for audit privacy/failure
semantics, retention, relative template dates, guiding-thread rollout and upgrade
diagnostics.

## Keeping this documentation accurate

All contributors, including AI agents, must follow [AGENTS.md](AGENTS.md).
Copilot also discovers [.github/copilot-instructions.md](.github/copilot-instructions.md);
the [PR template](.github/pull_request_template.md) requires a documentation-impact
explanation, including why no change is warranted when appropriate.

The **Documentation Contract** CI job compares the generated reference with source,
requires supported app-setting ENV names in `.env.example`, checks documented
Make/npm/script names and inline local Markdown links/heading anchors in the
README, operator reference, shared AI instructions and PR template. It runs on every
CI event and gates integration/image publication; it does not merely require a
README file to be touched. Regeneration is local and uses Node built-ins plus
Compose config, with no external AI service, network link checker or real secrets.

**Limits:** command-name/link checks cannot prove every instruction executes
correctly, prose reflects behavior, credentials are valid or deployment succeeds.
Checked heading anchors require plain Markdown headings, not inline HTML.
Source links, same-PR documentation review, meaningful negative tests and the
application/upgrade suites reduce drift; none can guarantee a README never goes stale.
